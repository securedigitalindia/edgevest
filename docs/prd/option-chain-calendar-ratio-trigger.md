# Option-chain triggers → draft trades: 1:2 diagonal sweep (ITM 400 → OTM 100) + 4-leg 1:2:1:2 PE ratio diagonal

**Status:** built 2026-09-22. First triggers after all previous alert triggers were removed from `config.TRIGGERS` the same day (definitions in git history at `0912c0c`). Evaluated from live option-chain data; each fire creates a **draft trade only** — never an open trade, no margin until an admin publishes it from the Dashboard's Draft Strategies panel (`add_manual_trade(status="draft")`, same path as `strategy_cli.py create`). The draft itself sends no alert, but the **trigger fire** sends its own Telegram alert (below).

## The template (corrected, then extended, 2026-09-22 — every trigger is one shape)

Every configured trigger is the same `calendar_ratio_credit` shape, generated by one
`config._calendar_ratio_trigger(name, itm_points, ...)` helper — they differ **only** in
`itm_points`. There is no separate "plain calendar" trigger type; `NIFTY_CE_ITM0_RATIO_DIAG_1X2` is just
this family's `itm_points=0` member — renamed from `NIFTY_CE_CAL_1X2` once the far-strike gap was
corrected (below), since the runtime already labels every trade's note `DIAG` regardless of name,
and keeping a "CAL" name for a structurally identical diagonal was misleading.

- **Futures price:** the front-month NIFTY future's live LTP (Upstox `get_ltp`, one call per evaluation, not read from the DB).
- **Base strike:** next `strike_step` (100) above the futures price for CE (`ceil`; PE would `floor`). Fut 23340 → base 23400.
- **K1 (near, BUY `near_lots`=1):** `base − itm_points`. `itm_points=0` (`NIFTY_CE_ITM0_RATIO_DIAG_1X2`) is the base itself; 300/400 push it that far into the money.
- **K2 (far, SELL `far_lots`=2):** `K1 + far_strike_offset` (**400**, the same gap for every itm_points). Fut 23340, itm_points=0 → K1 23400 / K2 23800.
- **Expiries:** near = nearest expiry with **DTE > `min_dte`** (1); far = the next expiry after it — unchanged, and shared by every `itm_points` value.
- **Net** = `near_lots × near_ltp − far_lots × far_ltp`, in premium points (not rupees), from the latest `option_chain_5m` snapshot. Every variant prices as a **debit** on real data (see table below) — the far leg, 400 points further OTM, is always cheaper than 1x the near leg.
- **Fires** when the net **debit < `max_debit_pts` (25)** — a net credit also qualifies (see `live/chain_triggers.py`'s `threshold` line). Sides: **CE only**. **One draft per trigger per side per IST day.**

**First build was wrong** (fixed same day): this trigger (then still named `NIFTY_CE_CAL_1X2`) originally had `far_strike_offset=0`
— same strike on both expiries, a pure calendar — which priced as a large ~200pt **credit** almost
every day (the concern raised earlier: "credit > 5" would be true every morning). The user then gave
a concrete example (fut 23340 → strikes 23400/23900, i.e. a 500-point gap) showing the far leg needs
its own strike; a 500 gap was tried first, then corrected to the same 400-point gap as the other two
once the user pointed out the ITM and plain-calendar triggers are the same shape (later extended into a full ITM-400-to-OTM-100 sweep — see Config summary). Verified directly against `option_chain_5m`
(2026-09-21 15:30 IST close, fut treated as 23450/23340 for the two checks):

| itm_points | K1 | K2 | near premium | far premium | near − 2×far |
|---|---|---|---|---|---|
| 0 (fut 23340 example) | 23400 | 23800 | 162.25 | 58.25 | **45.75 debit** |
| 0 (fut 23450) | 23500 | 23900 | 109.00 | 39.30 | **30.40 debit** |
| 300 | 23200 | 23600 | 300.25 | 122.00 | **56.25 debit** |
| 400 | 23100 | 23500 | 382.25 | 167.30 | **47.65 debit** |

All four rows are the same order of magnitude — confirms `itm_points=0` really is just another
member of this family, not a structurally different trigger. See the Config summary below for the
full sweep (now 6 triggers) and which one actually fires on this snapshot.

## Config summary — swept 2026-09-22 from 3 triggers to 6

Each entry is `config._calendar_ratio_trigger(name, itm_points, far_strike_offset=400, max_debit_pts=... | min_credit_pts=..., ...)` — the threshold has **no default** and every call must state its own explicitly (a `ValueError` if a call passes neither or both). This was changed 2026-09-22 from a silent `max_debit_pts=25` default: with 5 of 6 entries relying on the default and only OTM100 overriding it, the actual rule for most triggers wasn't visible at the call site — now every line in `CHAIN_TRIGGERS` states its own rule plainly. Same change applied to `_pe_ratio_diagonal_trigger()`'s `min_credit_pts` (now required, no default). `itm_points` sweeps ITM 400 down through OTM 100 in 100-point steps (matching `strike_step`), negative = out of the money (`K1 = base − itm_points`, so `itm_points=-100` pushes K1 past the base):

| Trigger | itm_points | K1 (fut 23450 → base 23500) | K2 | Fires when |
|---|---|---|---|---|
| `NIFTY_CE_ITM400_RATIO_DIAG_1X2` | 400 | 23100 | 23500 | debit < 25 |
| `NIFTY_CE_ITM300_RATIO_DIAG_1X2` | 300 | 23200 | 23600 | debit < 25 |
| `NIFTY_CE_ITM200_RATIO_DIAG_1X2` | 200 | 23300 | 23700 | debit < 25 |
| `NIFTY_CE_ITM100_RATIO_DIAG_1X2` | 100 | 23400 | 23800 | debit < 25 |
| `NIFTY_CE_ITM0_RATIO_DIAG_1X2` | 0 | 23500 | 23900 | debit < 25 |
| `NIFTY_CE_OTM100_RATIO_DIAG_1X2` | −100 | 23600 | 24000 | **credit > 5** (own rule) |

**OTM100 deliberately uses a different rule from the other five** — confirmed with the user
2026-09-22: while ITM400 through ITM0 all fire on `debit < 25` (the same rule the sweep was
originally verified with), OTM100 fires on `credit > 5` instead, matching the PE ratio diagonal's
rule. `config._calendar_ratio_trigger()` takes `max_debit_pts` or `min_credit_pts` (mutually
exclusive; `min_credit_pts` wins if both are passed) precisely so one entry in the sweep can use a
different threshold shape without a separate code path.

Verified against the same 2026-09-21 15:30 IST close snapshot, `near − 2×far`: ITM400 47.65, ITM300
56.25, ITM200 56.90, ITM100 45.75, ITM0 30.40, OTM100 14.10 — every value a debit, in the same
~15-60pt range, confirming the strikes/expiries behave as one family regardless of which threshold
each trigger uses. Under the **current** rules, none of the six fire on this snapshot: OTM100's
14.1pt debit clears `debit < 25` but not `credit > 5` (a debit is never a credit) — verified directly
(full evaluator run, Telegram mocked): all six log their number, none create a draft. A relaxed
`min_credit_pts=-25` test on OTM100 alone confirmed the fire mechanism still works correctly when the
rule *is* met (same draft as before: BUY 23600 CE 29 Sep @68.10 / SELL 2× 24000 CE 6 Oct @27.00).

*(Earlier version of this doc, before the OTM100 rule split: OTM100 was on `debit < 25` like the
other five and did fire on this snapshot — superseded by the above.)*

Drafts are noted `1:2 DIAG CE <K1>/<K2> (auto · debit <n>)` (or `CAL` if `far_strike_offset=0`, kept in `live/chain_triggers.py` for a same-strike variant if ever wanted — none configured today). Adding another itm_points value (further OTM, or a finer 50pt step) is one `_calendar_ratio_trigger(...)` line in `config.py`, no other duplication — each keeps its own independent once-per-side-per-day fire slot in `chain_trigger_fires`.

## Second trigger type: 4-leg 1:2:1:2 PE ratio diagonal (added 2026-09-22)

`NIFTY_PE_RATIO_DIAG_4LEG_400` — the same 4-leg shape as the already-backtested strategy
(`docs/prd/pe-ratio-diagonal-strategy.md`, `analysis/nifty_pe_ratio_diagonal_*`), wired up as a
live auto-draft trigger for the first time. Type `pe_ratio_diagonal_credit`, built by
`config._pe_ratio_diagonal_trigger(name, leg_gap=400, min_credit_pts=5, ...)`:

| Leg | Side | Lots | Strike | Expiry |
|---|---|---|---|---|
| 1 | BUY | 1 | K (base, next 100 below fut for PE) | expiry1 — nearest with DTE > `min_dte` (1) |
| 2 | SELL | 2 | K2 = K − `leg_gap` (400) | expiry2 — next after expiry1 |
| 3 | SELL | 1 | K | expiry2 |
| 4 | BUY | 2 | K2 | expiry3 — next after expiry2 |

Reuses `resolve_expiry_triplet()` and `SIDE_CONFIG` from the existing backtest modules directly
(same `sys.path` wrinkle as `backend/strategies/registry.py` — `backend/analysis/` is a flat
script directory) rather than reimplementing expiry/strike logic. Net = `l1 − 2×l2 − l3 + 2×l4`
(points); credit = `−net`. Fires when credit > `min_credit_pts` (5), same threshold shape as
`NIFTY_CE_ITM400_RATIO_DIAG_1X2` etc.

**On real data this 1:2:1:2 ratio prices as a debit, not a credit** — verified against the 2026-09-21
15:30 IST close snapshot (fut 23450, K 23400, K2 23000, expiries 29 Sep / 6 Oct / 13 Oct):
`l1=121.55, l2=56.65, l3=157.90, l4=84.45` → net = **−19.25 (a 19.25pt debit)**. So `credit > 5` is
expected to rarely fire under normal conditions with this exact ratio — confirmed to the user before
building (a 1:2:1:1 ratio would have priced as a 65.2pt credit, clearing the threshold easily, but
that's a different, untested risk shape — leg 3's short only half-covered — so 1:2:1:2 was kept
per the user's explicit confirmation). Verified end-to-end (Telegram mocked): the real snapshot
correctly produces no draft; a relaxed threshold produced the exact expected 4-leg draft (BUY 23400
PE 29 Sep @121.55 / SELL 2× 23000 PE 6 Oct @56.65 / SELL 23400 PE 6 Oct @157.90 / BUY 2× 23000 PE
13 Oct @84.45, debit 19.25) with the alert correctly showing the draft linked.

Draft note: `1:2:1:2 RATIO DIAG PE <K>/<K2> (auto · debit <n>)`. CE mirror is possible (same
`_RATIO_SIDE_CONFIG` already has a CE entry) but not configured — add `"sides": ["PE", "CE"]` or a
separate template call to enable it.

## Naming and console visibility (2026-09-22)

All seven triggers are variations on "ratio diagonal" — renamed for consistency: the CE family is
`NIFTY_CE_<ITM/OTM><N>_RATIO_DIAG_1X2`, the PE one is `NIFTY_PE_RATIO_DIAG_4LEG_400`. (Previously
the CE names had `_DIAG_1X2` without "RATIO", inconsistent with the PE name.)

Every evaluation now prints one line per trigger per side **whether or not it fires** — e.g.
`NIFTY_CE_ITM0_RATIO_DIAG_1X2 CE: K=23500/23900 fut=23450.0 near=109.0 far=39.3 -> debit 30.4
(debit < 25: not met)`. Before this, only a fire produced any output, so there was no way to see
how close a trigger was on a normal 5-min cycle — a fire's own log line (`... FIRED ...`) still
follows immediately after, unchanged.

## Telegram alert on every fire (added 2026-09-22)

Every trigger that fires sends one Telegram message (`live/alert.py:send_chain_trigger_alert`, "🎯 Trigger Fired") from the same code path that creates the draft, so it goes out once per trigger per side per IST day — never per 5-min snapshot. Contents: trigger name, the setup note, both legs with lots/strike/expiry/price, net credit/debit, the rule that fired (`debit < 25` for every currently configured trigger), the futures price, the chain snapshot time (IST), and an explicit **draft status**:
- **"Draft trade linked: #SEP26-16"** (+ Dashboard link when `FRONTEND_URL` is set) when the draft was created; or
- **"No draft trade linked"** with the error when draft creation failed. The fire claim is then released so the next snapshot retries; the failure alert is sent **once per trigger/side/day** (in-memory, resets on poller restart), retries are silent, and a successful retry sends the normal "linked" alert.

A failed Telegram send never affects the draft or the trigger loop. A trigger whose condition stays true after it has fired today sends nothing further.

## Mechanics

- `config.CHAIN_TRIGGERS` holds the definition; `live/chain_triggers.run_chain_triggers()` is called by `live/poller.py` right after each `option_chain_capture.run_capture()` (every 5 min, market hours only, wrapped in try/except so it can never crash the poll loop).
- Skips when the latest chain snapshot is older than 10 minutes (capture failure), fewer than two expiries qualify, or either leg has no traded price.
- Dedup: `chain_trigger_fires` (`UNIQUE(trigger_name, side, ist_date)`) — the fire is claimed *before* the draft is created and released if creation fails. A discarded or published draft does not free the day's slot.
- Draft: note `1:2 DIAG CE <K1>/<K2> (auto · debit <n>)`, `risk_level: high` (net short far leg), leg prices = the snapshot LTPs, `trigger_name` = `MANUAL` (drafts flow through `add_manual_trade`).
- Adding a side or another `itm_points` value is a config change — a `sides` edit on an existing entry, or one more `config._calendar_ratio_trigger(...)` call.

## Where prices come from — DB vs live Upstox (clarified 2026-09-22)

| Value | Source | Freshness |
|---|---|---|
| Futures price (`fut_ltp`) | **Live Upstox** call, `live.upstox_client.get_ltp()` | Fetched fresh on every single evaluation |
| Which future contract to query (`fo_instruments.nifty_front_fut()`) | Local cached NSE F&O instrument list file, originally downloaded from Upstox | Re-downloaded once a day (or reused if today's cache file already exists) — not a live call per evaluation |
| Every option premium (near/far, or l1–l4) | **Database**, `option_chain_5m` table via `queries.get_chain_ltp()` | Whatever the poller's separate 5-min `option_chain_capture.run_capture()` job already wrote — never fetched live at evaluation time |
| Latest snapshot timestamp, expiry list | Database, same table | Read, not fetched |

Only the futures price is live per evaluation; every option premium comes from the local capture. This is why `_MAX_SNAPSHOT_AGE` (10 min) exists — if the capture job lags or fails, the option prices in the DB could be stale even though the futures price is always current.

**Fixed 2026-09-22 (was: 7 separate live Upstox calls per 5-min cycle).** `run_chain_triggers()` previously called each trigger's evaluator independently, and each evaluator fetched its own `fut_ltp`; since every trigger uses `symbol="NIFTY50"`, all 7 fetched the identical front-month future price separately. Now `run_chain_triggers()` fetches `fut_ltp` once per distinct symbol (`_fetch_fut_ltp()`), caches it in a local dict for the duration of that call, and passes it into each evaluator (`_evaluate_calendar_ratio_credit(cfg, fut_ltp)` / `_evaluate_pe_ratio_diagonal_credit(cfg, fut_ltp)` — both now take `fut_ltp` as a parameter instead of fetching it themselves). If the fetch for a symbol fails, every trigger on that symbol is skipped for that cycle (same behavior as before, just centralized). Verified: `get_ltp` call count dropped from 7 to 1 per cycle; every trigger's logged credit/debit is byte-identical to before; draft creation and the Telegram alert still work correctly (tested with a relaxed threshold).

## How to watch it run in prod

The poller is its own systemd unit, separate from the web API: `sudo journalctl -u edgevest-poller -f` (follow live), `-n 200` (last 200 lines, no follow), `--since "10 min ago"`, or pipe through `grep chain_triggers` for just the trigger lines. `sudo systemctl status edgevest-poller` confirms it's running and since when. Trigger lines only appear during market hours (09:15–15:30 IST), right after each 5-min option-chain capture — not on their own separate timer.

## Trades UI — description next to the display code (added 2026-09-22)

Every recommendation card (`frontend/src/screens/Trades.jsx`) now shows its `note` in brackets right next to the `#<display_code>`, e.g. `#SEP26-15 (1:2 DIAG CE 23600/24000 · auto · debit 14.1)` — in addition to the same note already shown as the card's title. Only rendered when `rec.note` is set. New CSS class `.rec-code-desc` (`Trades.css`), styled muted to match the adjacent adjustment-count text.

## Things to know

- Uncovered risk: the 1x near long only partly covers the 2x far short (calendar family), and the PE ratio diagonal's legs 1/3 are only partly covered by legs 2/4 — the two legs/pairs are on different expiries in every trigger here, and no margin/max-loss is computed for a draft until publish.
- The near-leg exit/roll is manual — nothing here manages the position after publish.
- On real captured data (2026-09-21 15:30 IST close), none of the 7 configured triggers fire — every one is expected to fire only occasionally, not on a predictable schedule, since real premiums rarely cross these thresholds. A quiet poller log is the normal case, not a bug — see "How to watch it run in prod" above for confirming it's actually evaluating.

## Deploy notes

Needs `python poller.py init` on prod (creates `chain_trigger_fires`) and a poller restart. A backend (`edgevest-web`) restart is not required for this feature itself.
